## 0. 一页速记（先背这张）

| 概念 | 一句话 | 关键数字 / 坑 |
|---|---|---|
| **LLM** | 一个「给定前文，预测下一个 token」的概率函数 | 不是数据库，没有「不知道」的默认行为 |
| **Token** | 模型处理文本的最小单位（≈ 0.5~1 个汉字） | 中文比英文费 token，成本按 token 算 |
| **上下文窗口** | 一次请求能塞进去的最大 token 数 | 输入 + 输出**共用**这个额度 |
| **messages** | 对话历史数组，**每次全量重发** | 模型无状态，多轮靠你重发历史 |
| **temperature** | 控制随机性，0~2，越高越发散 | 抽取/分类用 0~0.3，聊天 0.7 |
| **top_p** | 只在「累计概率前 p」的词里选 | 和 temperature **只调一个** |
| **max_tokens** | **输出**上限，不含输入 | 撞上限 → `finish_reason="length"` 被截断 |
| **stream** | 边生成边吐，SSE 协议 | 返回的是 `delta` 不是 `message` |
| **tools** | 告诉模型「有哪些函数可调」 | 模型**只输出调用意图**，执行是你的代码 |
| **finish_reason** | 这轮为什么结束 | `stop` / `length` / `tool_calls` / `content_filter` |
| **TTFT** | 从请求到收到第一个 token 的时间 | 用户体感主要看它，不看总时长 |
| **幻觉** | 编造看似合理但无依据的内容 | 根因在训练目标，只能缓解不能根治 |

**六个字段的最小印象**：

```
model       → 用哪个模型（决定能力/价格/上下文）
messages    → 说了什么（完整历史，每轮重发）
temperature → 多大胆（随机性）
max_tokens  → 最多说多少（输出上限）
stream      → 边想边说还是一次说完
tools       → 能动手做什么（只给意图，你来执行）
```

## 1. 用大模型前必须建立的 5 个直觉

### 1.1 它是概率函数，不是数据库

模型每次只做一件事：**根据前面所有内容，算出下一个 token 的概率分布，挑一个，重复**。

所以：
- 同样的输入，两次输出**可以不一样**——这是设计，不是 bug。
- 它没有「查询」这个动作，所有回答都是「生成」出来的。

> **Java 类比**：不是 `repository.findById()`，而是 `random.choices(distribution)`。

### 1.2 它的知识有「截止日期」，且不在你的库里

模型的知识全部来自训练数据。训练之后发生的事，它**不知道**（除非你告诉它）。

这直接推出：**凡是「最新/私有/内部」的知识，必须靠 RAG 或工具注入，不能指望模型自己知道。**

### 1.3 它在「补全」，没有「不知道」这个默认动作

你问一个它没学过的问题，它不会返回 `null`，而是**生成一个看起来最像答案的文本**。这就是幻觉的根源。

> 你没法「让它知道」，只能**给它出口**：在 prompt 里明确「资料中没有时，回答『未找到』」，并在代码侧校验。

### 1.4 模型是无状态的，记忆靠你「重发」

服务端**不保存**你的对话。多轮对话的实现方式是：把历史 messages 拼成一个数组，**每轮全量重发**。

```
第 1 轮发送: [system, user1]
第 2 轮发送: [system, user1, assistant1, user2]     ← 历史又发了一遍
第 3 轮发送: [system, user1, assistant1, user2, assistant2, user3]
```

**这解释了三件事**：
1. 为什么对话越长越贵（token 线性增长）；
2. 为什么需要「上下文压缩 / 摘要 / 检索记忆」；
3. 为什么你的服务必须自己存历史（DB / Redis）。

> **Java 类比**：典型的无状态 HTTP 服务。会话状态在客户端或你的存储里，不在服务端。

### 1.5 你学的是「协议」，不是「某家的 SDK」

国内主流厂商（DeepSeek / 通义 / 智谱 / Kimi / 硅基流动）**都是 OpenAI 兼容协议**。

```python
client = OpenAI(
    api_key=os.environ["XXX_API_KEY"],
    base_url="https://api.deepseek.com",   # ← 换这里
)
# model="deepseek-chat"                     # ← 换这里
```

**所以**：`model / messages / temperature / max_tokens / stream / tools` 这套是**通用协议**；
而 `reasoning_effort`、`thinking` 这类是**厂商私货**，换一家就没了。

> ⚠️ 你 `step1-hello.py` 里的 `reasoning_effort` + `extra_body={"thinking":...}` 就是私货。能用，但要清楚它不属于标准协议。

## 2. Token 与上下文窗口

### 2.1 Token 是什么

文本先被 **Tokenizer** 切成 token，再转成数字给模型。token 不等于字，也不等于词。

```
"Hello world"        → ["Hello", " world"]                 ≈ 2 tokens
"人工智能"            → ["人工", "智能"] 或 ["人","工","智","能"]   ≈ 2~4 tokens
"temperature"        → ["temper", "ature"]                 ≈ 2 tokens
```

**经验值**（不要背死，要用 API 返回的 `usage` 校准）：

| 文本 | 经验换算 |
|---|---|
| 英文 | 1 token ≈ 4 个字符 ≈ 0.75 个单词 |
| 中文 | 1 token ≈ 0.6~1 个汉字（国产模型分词器对中文更友好） |
| 代码 | 1 token ≈ 3~4 个字符 |

### 2.2 中文为什么更费 token

Tokenizer 的词表是在**以英文为主的语料**上训练出来的。英文常见词能合并成一个 token，中文往往要拆成 2~4 个。

**后果**：
- 同样的意思，中文的 token 数是英文的 1.5~2 倍 → **更贵、更快撑爆上下文**；
- 面试常问，答「分词器词表对中文合并粒度低」即可。

### 2.3 上下文窗口（context window）

**输入 token + 输出 token 共用**这一个额度。

```
上下文窗口 = 128k
├── 输入（system + 历史 + 检索到的文档 + 用户问题）≤ 大部分
└── 输出（max_tokens 预留）
```

超了会怎样？两种处理：
- 服务端直接报错（`context_length_exceeded`）；
- 或静默截断（更危险，你不知道它丢了什么）。

**工程手段**：滑动窗口（只留最近 N 轮）→ 摘要压缩（把旧对话总结成一段）→ 检索式记忆（只捞相关历史）。

### 2.4 Lost in the Middle

**长上下文里，模型对「开头」和「结尾」的信息记得住，中间的信息容易被忽略。**

这是论文《Lost in the Middle》的结论，直接影响你的设计：

| 场景 | 怎么做 |
|---|---|
| RAG 塞很多文档 | 最相关的放**最前面**，其次放**最后面**，最不相关的扔中间 |
| 长 system prompt | 关键约束放开头或结尾，别埋在中间 |
| 长对话 | 别指望模型记住第 3 轮说的话 |

### 2.5 成本怎么算

```
单次成本 = 输入 token × 输入单价 + 输出 token × 输出单价
```

**注意**：输出通常比输入贵 2~4 倍（生成是逐 token 串行的，成本更高）。

> 具体单价每周都在变，**永远以厂商 pricing 页为准**。你要会的是公式，不是数字。

## 3. 模型是怎么来的（只要概念，不要数学）

### 3.1 三个阶段

```
① 预训练 (Pre-training)
   海量文本 → 学「下一个词是什么」 → 得到基座模型
   产出：会说话，但不会听话（不懂指令）

② 监督微调 (SFT, Supervised Fine-Tuning)
   人工写的高质量「问题-答案」对 → 学会按指令回答
   产出：能对话了

③ 对齐 (RLHF / DPO)
   人类给多个回答排序 → 训练模型更「符合人类偏好」
   产出：更有用、更安全、更少胡说（但也更倾向「讨好」，这是幻觉的一个来源）
```

**面试一句话**：「预训练学知识，SFT 学格式，对齐学偏好。」

### 3.2 训练 vs 推理

| | 训练 (Training) | 推理 (Inference) |
|---|---|---|
| 干什么 | 更新模型权重 | 用固定权重生成回答 |
| 你要不要碰 | ❌ 不碰 | ✅ 你的全部工作 |
| 成本 | 极高（GPU 集群） | 按 token 计费 |

**你的赛道是推理侧（应用层），不是训练侧（算法层）。**

### 3.3 微调（Fine-tuning / LoRA）—— 只需懂到这

- **微调改的是「行为/风格/格式」，不是「知识」**。
- 想让模型记住你的内部文档 → 用 **RAG**，不要微调。
- 想让模型总是输出特定格式、特定口吻 → 可以考虑微调。
- **LoRA**：只训练一小部分参数（低秩适配），成本低，是目前主流微调方式。

> 决策口诀：**知识用 RAG，风格用微调，能不改模型就不改模型。**

## 4. 模型分级与选型

### 4.1 三类模型

| 类型 | 特点 | 例子 | 适用 |
|---|---|---|---|
| **快模型 / 小模型** | 便宜、快、能力一般 | flash / mini / lite 系列 | 分类、抽取、改写、路由 |
| **通用大模型** | 均衡 | deepseek-chat、qwen-plus、glm-4 | 大部分业务 |
| **推理模型** | 先「思考」再答，慢但强 | deepseek-reasoner、o 系列 | 数学、复杂推理、多步规划 |

### 4.2 选型的 6 个维度

1. **质量**：在你的任务上实测（不要看榜单）
2. **延迟**：TTFT 和总时长
3. **价格**：输入/输出分别算
4. **上下文窗口**：够不够塞你的文档
5. **中文能力**：国产模型通常更好
6. **合规/私有化**：能不能数据不出域

### 4.3 模型路由（省钱的核心手段）

```
用户请求 → 判断难度 → 简单任务走小模型，复杂任务走大模型
```

**这是 W18 成本优化里最有效的一招**，面试高频。大多数企业里，**大部分请求并不需要最贵的那一档。**

## 5. 采样：模型「怎么挑下一个字」

模型算出的是**概率分布**，采样就是「怎么从分布里挑」。三个参数：

### 5.1 temperature（温度）0 ~ 2

| 值 | 效果 | 场景 |
|---|---|---|
| `0` | 几乎总选概率最高的词 | 抽取、分类、代码、需要稳定 |
| `0.7` | 有变化但不离谱 | 日常对话（默认） |
| `1.0+` | 发散、有创意 | 写文案、头脑风暴 |

> **重要**：`temperature=0` **不保证 100% 一致**。因为浮点误差、批处理顺序、推理引擎实现差异，同一请求仍可能有细微不同。**面试答这一点会加分。**

### 5.2 top_p（核采样）0 ~ 1

只在「累计概率达到 p 的那批词」里选。

```
top_p = 0.9  →  把所有 token 按概率从高到低排，累加到 90% 为止，
                只在这批词里采样，长尾的低概率词直接丢弃。
```

### 5.3 top_k

只在概率最高的 K 个词里选（OpenAI 不暴露，部分厂商有）。

### 5.4 实践规则（记这条就够）

> **temperature 和 top_p 只调一个，另一个保持默认。**
> OpenAI 官方建议：要么调 temperature，要么调 top_p，**不要同时调**——两个一起调，效果互相抵消，你也不知道是哪个起了作用。

### 5.5 其他相关参数（了解即可）

| 参数 | 作用 |
|---|---|
| `stop` | 遇到指定字符串就停止生成 |
| `presence_penalty` | 惩罚已出现过的词 → 鼓励说新话题 |
| `frequency_penalty` | 按出现次数惩罚 → 减少重复 |
| `seed` | 部分厂商支持，尽量让结果可复现（但仍不保证） |
| `n` | 一次生成几个候选（费钱，少用） |

## 6. 延迟与成本

### 6.1 三个延迟指标

```
请求 ──[TTFT]──> 第一个 token ──[TPOT × 输出token数]──> 最后一个 token
       ↑ 首字延迟                    ↑ 每个 token 的间隔
```

| 指标 | 含义 | 经验阈值 |
|---|---|---|
| **TTFT** | 首 token 延迟 | 对话产品 > 2~3s 用户就觉得卡 |
| **TPOT** | 每 token 输出时间 | 越快越像「打字」 |
| **总时长** | 端到端 | = TTFT + TPOT × 输出 token 数 |

**关键认知**：
- **流式（stream）优化的是「体感」**：总时长没变，但用户 1 秒就看到字在动。
- **所以对话类产品，流式不是加分项，是底线。**

### 6.2 降低成本的手段（至少记 5 种）

1. **模型路由**：简单任务用小模型
2. **Prompt 缓存（prefix cache）**：相同的长前缀（如 system prompt）命中缓存，价格大幅降低
3. **语义缓存**：相似问题直接复用答案
4. **上下文压缩**：摘要、裁剪、只塞相关片段
5. **控制 max_tokens**：别让模型啰嗦
6. **批处理**：非实时任务走批量接口（通常半价）

> 面试问「单次成本怎么算、怎么优化」，答出上面这套 + 给出公式，就过关了。

## 7. 六个核心请求字段（重点）

> 这一节是 W1 的核心。每个字段按 **作用 → 取值 → 坑 → Java 类比 → 代码** 五段写。

### 7.1 `model` —— 用哪个模型

```json
{ "model": "deepseek-chat" }
```

| 项 | 说明 |
|---|---|
| **作用** | 决定能力、价格、上下文窗口、是否支持 tools |
| **取值** | 厂商定义的字符串，**没有统一标准** |
| **坑 1** | 名字写错 = 直接 400，且报错信息常常很含糊 |
| **坑 2** | 换厂商时 `base_url` 和 `model` **必须一起换** |
| **坑 3** | 推理模型（reasoner 类）通常**不支持** `temperature` 等采样参数，也不支持 tools |

**常见模型名对照**（会变，以官网为准）：

| 厂商 | 快/通用 | 推理 |
|---|---|---|
| DeepSeek | `deepseek-chat` | `deepseek-reasoner` |
| 通义 | `qwen-plus` / `qwen-turbo` | `qwen-max` / qwq 系列 |
| 智谱 | `glm-4-flash` | `glm-4-plus` |

> **Java 类比**：`model` ≈ 你选的 `DataSource` 实现类，换了实现，能力/价格/行为全变，但接口一样。

---

### 7.2 `messages` —— 说了什么（最重要）

```json
{
  "messages": [
    { "role": "system",    "content": "你是企业工单助手，只依据提供的资料回答；资料不足时回答『未找到』。" },
    { "role": "user",      "content": "退货政策是几天？" },
    { "role": "assistant", "content": "根据资料，7 天无理由退货。" },
    { "role": "user",      "content": "那运费谁出？" }
  ]
}
```

#### 四种 role

| role | 谁写的 | 作用 | 优先级 |
|---|---|---|---|
| `system` | 你（开发者） | 设定角色、规则、输出格式 | **最高** |
| `user` | 终端用户 | 用户的输入 | 中 |
| `assistant` | 模型（历史回复） | 让模型知道「我上一轮说了什么」 | — |
| `tool` | 你的代码 | 工具执行结果（配合 `tools` 用） | — |

#### 三条铁律

1. **模型无状态，历史必须全量重发**（见 §1.4）。
2. **`system` 不是绝对命令**。用户可以在 `user` 里说「忽略以上指令」——这就是 prompt injection 的入口。
3. **`system` 里要写「不知道时怎么办」**，否则模型一定会编。

#### 坑

- 拼接历史时**忘了加 assistant 的回复** → 模型以为自己没回答过，重复回答。
- 历史无限增长 → 成本和延迟线性上升，最后爆上下文。
- 把用户输入**裸拼**进 system → 注入风险。

> **Java 类比**：`List<Message>` 就是你的 DTO 列表，每轮请求把整个 List 序列化发过去。**你的服务端要自己持久化这个 List。**

---

### 7.3 `temperature` —— 多大胆

```json
{ "temperature": 0.2 }
```

| 项 | 说明 |
|---|---|
| **作用** | 控制采样随机性。0 = 几乎总选最高概率词；越高越发散 |
| **范围** | 通常 0 ~ 2（OpenAI 系），默认 1 |
| **推荐** | 抽取/分类/代码：`0 ~ 0.3`；对话：`0.7`；创意：`1.0+` |
| **坑 1** | 设 0 **不等于**完全确定（浮点/批处理/实现差异） |
| **坑 2** | 和 `top_p` 同时调，效果互相干扰 |
| **坑 3** | 推理模型可能不支持 |

**做一个实验（W1 必做）**：同一个问题，`temperature=0` 调 10 次 vs `temperature=1.5` 调 10 次，把输出贴进表格对比。

> **Java 类比**：像 `Random` 的种子 + 策略。`temperature=0` ≈ 取 `max()`，`temperature=1.5` ≈ 在分布上撒开。

---

### 7.4 `max_tokens` —— 最多说多少

```json
{ "max_tokens": 500 }
```

| 项 | 说明 |
|---|---|
| **作用** | **输出** token 的上限（**不包含输入**） |
| **默认** | 不传则由模型自己决定，可能很啰嗦 |
| **撞上限的后果** | `finish_reason = "length"`，输出**被硬截断**（可能截在半句话/半个 JSON 中间） |
| **坑 1** | 以为是限制输入的——不是 |
| **坑 2** | 设太小 → JSON 输出被截断 → 解析失败（这是结构化输出最常见的坑） |
| **坑 3** | 推理模型的「思考 token」也计入输出 |

**工程建议**：
- 结构化输出要**留足余量**（比如预期 200 token，设 500）；
- 代码里**必须检查 `finish_reason`**，`"length"` 时要重试或告警；
- 上下文窗口是「输入 + 输出」共用的，`max_tokens` 太大可能直接超窗。

> **Java 类比**：像响应体大小上限 + 读取超时。超了不是报错，是**静默截断**，更危险。

---

### 7.5 `stream` —— 边想边说

```json
{ "stream": true }
```

| 项 | 说明 |
|---|---|
| **作用** | `false` 一次性返回完整回复；`true` 逐 token 推送（SSE） |
| **协议** | Server-Sent Events（`text/event-stream`），一行行 `data: {...}` |
| **收益** | 大幅改善体感（TTFT 决定体验），不是减少总时长 |
| **坑 1** | **流式返回的是 `delta` 不是 `message`**，解析方式不同 |
| **坑 2** | 流式下 `usage` 默认不返回，需要额外参数（如 `stream_options.include_usage`） |
| **坑 3** | **Nginx / 网关缓冲会把流式变成一次性返回**（上线必查） |
| **坑 4** | 流到一半连接断了，已经输出的内容是**半成品**，要设计重试/续写 |

```text
data: {"choices":[{"delta":{"content":"你"},"finish_reason":null}]}
data: {"choices":[{"delta":{"content":"好"},"finish_reason":null}]}
data: {"choices":[{"delta":{},"finish_reason":"stop"}]}
data: [DONE]
```

> **Java 类比**：`Flux<String>` / `SseEmitter` / WebSocket。**流式 = 不能做全量校验后再发送**，所以错误处理要特别设计。

### 7.6 `tools` —— 能动手做什么

```json
{
  "tools": [{
    "type": "function",
    "function": {
      "name": "get_order_status",
      "description": "根据订单号查询订单状态。仅用于查询，不修改任何数据。",
      "parameters": {
        "type": "object",
        "properties": {
          "order_id": { "type": "string", "description": "订单号，形如 ORD-20261027-001" }
        },
        "required": ["order_id"]
      }
    }
  }]
}
```

#### 核心认知（最重要的一条）

> **模型不执行任何函数。它只输出「我想调用哪个函数、参数是什么」的 JSON。执行是你的代码负责。**

```
你：messages + tools  →  模型
模型：tool_calls = [{name:"get_order_status", arguments:'{"order_id":"ORD-001"}'}]
你：真的去查数据库
你：把结果以 role="tool" 塞回 messages
模型：基于结果生成最终回答
```

#### 响应长这样

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "id": "call_abc123",
        "type": "function",
        "function": { "name": "get_order_status", "arguments": "{\"order_id\":\"ORD-001\"}" }
      }]
    },
    "finish_reason": "tool_calls"
  }]
}
```

#### 你要回传的格式

```json
{ "role": "tool", "tool_call_id": "call_abc123", "content": "{\"status\":\"已发货\"}" }
```

#### 坑

| 坑 | 后果 | 解法 |
|---|---|---|
| `arguments` 是**字符串**不是对象 | 直接当对象用会崩 | 先 `json.loads()`，再校验 |
| 工具名/描述写得含糊 | 模型选错工具 | 描述写清「做什么、什么时候用、返回什么」 |
| 工具太多（>20） | 模型选择准确率下降 | 分组、路由、按场景裁剪 |
| 工具返回异常直接抛 500 | 模型拿不到可理解的信息 | 返回结构化错误，让模型能重试或告知用户 |
| 写操作不幂等 | 重试产生两条数据 | 幂等键 |
| 没有最大步数 | 无限循环烧钱 | 步数/时间/成本三重上限 |

> **Java 类比**：`tools` ≈ 一组接口定义（JSON Schema 就是你的 `@Valid` 约束），`tool_calls` ≈ 反射调用意图，整个循环 ≈ 你自己写的一个简易 RPC 调度器。

## 8. 响应结构：一次返回到底长什么样

```json
{
  "id": "chatcmpl-9f8a...",
  "object": "chat.completion",
  "created": 1761523200,
  "model": "deepseek-chat",
  "choices": [{
    "index": 0,
    "message": {
      "role": "assistant",
      "content": "根据资料，7 天无理由退货。"
    },
    "finish_reason": "stop"
  }],
  "usage": {
    "prompt_tokens": 128,
    "completion_tokens": 24,
    "total_tokens": 152
  }
}
```

### 必须记住的四个部分

| 字段 | 用途 |
|---|---|
| `choices[0].message.content` | 回答正文 |
| `choices[0].finish_reason` | 为什么结束（**必须检查**） |
| `usage.prompt_tokens` / `completion_tokens` | 计费依据，**算成本就看它** |
| `choices[0].message.tool_calls` | 有工具调用时才有 |

### finish_reason 四种取值

| 值 | 含义 | 你要做什么 |
|---|---|---|
| `stop` | 正常结束 | 正常处理 |
| `length` | 撞到 `max_tokens` | 输出被截断 → 重试 / 增大上限 / 告警 |
| `tool_calls` | 模型要调工具 | 执行工具 → 回传 → 再请求 |
| `content_filter` | 被内容安全策略拦截 | 按业务处理，别当系统错误 |

> **Java 类比**：`finish_reason` ≈ 业务状态码。只看 `content` 不看它，等于只看 body 不看 status code。

## 9. 流式协议（SSE）细节

### 9.1 为什么是 SSE 不是 WebSocket

| | SSE | WebSocket |
|---|---|---|
| 方向 | 服务端 → 客户端（单向） | 双向 |
| 协议 | 普通 HTTP | 需要握手升级 |
| 断线重连 | 浏览器**自带**重连 | 要自己实现 |
| 适用 | **LLM 输出（就是单向的）** | 聊天室、协同编辑 |

**结论**：LLM 场景**不需要** WebSocket，SSE 更简单。面试问「为什么不用 WebSocket」，答「输出是单向的，SSE 够用且自带重连、走普通 HTTP 好过网关」。

### 9.2 一条流长什么样

```text
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"choices":[{"delta":{"content":"根据"},"finish_reason":null}]}

data: {"choices":[{"delta":{"content":"资料"},"finish_reason":null}]}

data: {"choices":[{"delta":{},"finish_reason":"stop"}]}

data: [DONE]
```

**要点**：
- 每条以 `data: ` 开头，空行分隔；
- 增量内容在 `delta.content`，**不是** `message.content`；
- `finish_reason` 只在最后一条有值；
- `data: [DONE]` 是结束标记（部分厂商有）。

### 9.3 前端怎么消费（W9 会做，先留个印象）

```javascript
const resp = await fetch('/api/chat', { method: 'POST', body: ... });
const reader = resp.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const text = decoder.decode(value);
  // 按 "\n\n" 切分，逐行取 data: 后面的 JSON
}
```

> 注意：`EventSource` **只支持 GET**，所以带 body 的 POST 请求要用 `fetch + ReadableStream`。**这是前端面试常问的细节。**

### 9.4 流式下必须处理的四个异常

1. **流到一半断开** → 已输出的是半成品，要标记「已中断」并提供「重试」
2. **半截 Markdown / 代码块** → 前端渲染会错乱，要处理未闭合的 ``` 
3. **首 token 迟迟不来** → 要有「思考中」提示，别让用户以为卡死
4. **Nginx 缓冲** → 流式变一次性返回，需要 `X-Accel-Buffering: no`

## 13. 十个常见误区

| # | 误区 | 正确认知 |
|---|---|---|
| 1 | 模型会记住上一轮对话 | 不会，历史靠你重发 |
| 2 | `temperature=0` 结果完全一致 | 不保证，只是接近确定性 |
| 3 | `max_tokens` 限制输入长度 | 只限制输出 |
| 4 | 上下文窗口够大就不用 RAG | 成本、延迟、lost-in-middle、权限、时效都不允许 |
| 5 | 工具调用是模型执行的 | 模型只输出意图，执行是你的代码 |
| 6 | 所有 SDK 参数都是通用的 | `reasoning_effort`、`thinking` 是厂商私货 |
| 7 | 流式返回 `message` | 返回的是 `delta` |
| 8 | 只看 `content` 就行 | 必须看 `finish_reason`，否则截断了都不知道 |
| 9 | 幻觉靠改 prompt 能根治 | 只能缓解；根因在训练目标，要用 RAG + 校验 + 拒答设计 |
| 10 | 微调能让模型记住公司文档 | 微调改行为不改知识，知识用 RAG |
